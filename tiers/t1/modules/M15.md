# M15 — Device identity, anti-clone enrolment and the kill switch

**Module:** M15 security · **Subsystem:** S06 · **Features:** F04, F17 · **Controls:** C14, C7
**Depends:** M13 audit chain, M10 (device binding of the decommission receipt) · **Blocks:** commissioning, egress
**Class:** Privacy-critical (brief + review)

## Identity has a root and a binding, and they are not the same thing

SPEC §4 gives L1 two facts — the SSD controller serial and the host DMI fingerprint — and the whole
behaviour of the profile follows from treating them differently. The controller serial is the *root*:
it travels with the appliance, so it is what T2 enrols and what a certificate is issued against. The
DMI fingerprint is a *binding*: it says which machine the appliance was commissioned into, and it is
expected to change when a customer replaces a PC.

That split is what lets two superficially similar events be told apart. The same root arriving at
enrolment twice is a **clone attempt**: someone imaged the disk, and refusing it is the only
anti-clone control an SSD with no secure element can offer. The same root booting with a *different*
binding on a device that is already enrolled is a **PC replacement**: not an attack in itself, and
not something to refuse permanently, but not something to accept silently either — the device enters
`RE_ENROLMENT_PENDING`, stops talking to T2, and keeps counting locally.

L2 and L3 root identity in the SoM serial and the security element, and the attached PC contributes
nothing at all. `host_fingerprint` returns `None` off L1, so a PC swap is not merely tolerated on
those profiles, it is not an input: nothing is compared, nothing is audited, and the device does not
notice.

## Pending is a halt on egress, not on the site

`egress_allowed` is false while re-enrolment is pending, and the egress filter checks it before it
checks anything else. The store keeps counting, retention keeps running, alerts keep firing; what
stops is the reporting path, which is the only thing a mis-bound identity could poison at T2.

Restoring trust needs a human at T2 and nothing on the device can substitute. The approval is signed
in its own domain (`re-enrolment-approval`, distinct from the commissioning-exception and
decommission domains, so no signature can be replayed across them) and names both the device and the
*specific* fingerprint being approved. Approving one PC swap therefore does not pre-authorise the
next machine the disk is plugged into — a second swap raises a second pending state.

An identity root that changes under a device that is already enrolled is refused outright rather than
made pending: the disk was moved into a different appliance, and no host-side approval can make that
coherent.

## The kill switch is durable state and asymmetric authority

A kill is written to disk before it is reported, and reloaded on construction, because "survives
reboot" (F17 R2) is a property of the file, not of the process. Scope is camera, zone or capability,
and `stream_allowed` is the single query an ingest path asks.

Killing needs an actor and a reason and nothing else; releasing needs TA authorisation. Stopping
processing is always safe and should be within reach of the person standing in the store; resuming
it is a privacy decision and belongs to the tenant. On L3 a hardware DI assertion overrides both
directions — no stream starts, and no software release clears it — so the operator's physical action
cannot be undone from a console.

Commissioning does not take anyone's word for either item. `exercise_kill_switch` kills a camera,
asserts that the stream is actually refused, releases it under TA authorisation and only then records
the gate item, and `record_identity` refuses the item unless the device is genuinely enrolled.

## Not proven here

There is no AWS IoT Fleet Provisioning call. `FleetRegistry` is an in-process stand-in for the T2
side of enrolment, so what these tests demonstrate is that the device *presents* one identity and
handles the answers correctly — the one-time issuance that actually blocks a clone lives at T2 and
is untested here. The certificate is a record, not an X.509 credential, and nothing performs a TLS
handshake with it.

No security element is touched. L2/L3 identity is a supplied module serial; SEC-1 and TPM 2.0
attestation, non-exportable key generation and any measured-boot binding do not exist in this code,
so `key_protection` states an intent rather than an observed property. On L1 the honest limitation
stands and is surfaced through `disclosure_required`: a stolen disk carries its enrolment key, and
nothing host-side changes that.

The kill switch has no hardware behind it. `assert_hardware` is a method, not a DI line, so the L3
path proves the software contract and not the wiring; the F17 latency budget for stopping ingest is
unmeasured because no decoder is attached to `stream_allowed` yet. Kill state is a JSON file on a
host filesystem, replaced atomically, but never exercised on the LUKS2 volume or under power loss.
