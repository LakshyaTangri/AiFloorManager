# M10 — Storage domains, durable retention and crypto-erase

**Module:** M10 storage · **Subsystem:** S04 · **Features:** F16 · **Controls:** C9, C10
**Depends:** M02/M03 (layout), M13 audit chain · **Blocks:** decommission, RMA
**Class:** Privacy-critical (brief + review)

## A domain is a set of properties, not a directory

Retention and erase both depend on facts about where a record sits, so the facts are stated once and
derived from the checked layout rather than assumed per call site. `DATA` and `SPOOL` are LUKS2 and
therefore crypto-erasable; `AUDIT` is append-only and deliberately *not* erasable, because the chain
has to outlive the device (F16 R3); `VOLATILE` is zram and does not survive a reboot, which is what
L1 needs when a trace may exist while a person is in frame and not afterwards.

The pairing that matters falls straight out of those properties: a class that must be forgettable
and a domain that must be permanent are mutually exclusive, so C3/C4/C5 on the audit domain is a
refusal (`domain_not_erasable`) rather than a caller's responsibility to avoid. Placement also
re-checks the trust level, so L1 cannot persist a trace through this path even if some future writer
forgets — and with a layout supplied, an unencrypted data volume or a volume on the customer's disk
refuses the write before a byte is committed (AD-01).

## The enforcer does not hold the writer's handle

F16 R1 wants retention enforced by something that is not application code, and its acceptance
criterion is a trace deleted "with the application stopped". A shared object cannot satisfy that, so
the index is SQLite on the data domain and `RetentionService` opens it *by path*. The consequence is
the point: a crashed analytics container cannot extend a retention period by being unavailable to
delete.

Ceilings are applied at admission, not at sweep — C3 by profile, C5 by clip policy, C4 by the basis
it carries — so the row on disk is already the truth if the enforcer never runs again. C5 has no
default: a site that has not stated how long clips live may not keep clips (`clip_policy_absent`),
which is a refusal rather than an implementer's guess at a number the SPEC does not publish.
Likewise a C4 record with no basis reference is refused, because it would otherwise outlive the
justification that permitted it.

Deletion is two-phase. The receipt is written *before* the row goes, with the row marked
`pending_delete`, because a crash that loses a receipt breaks F16 R2 whereas a crash between the two
leaves a marked row that the next sweep finishes without emitting a second receipt.

## Crypto-erase claims only what key destruction can support

Erase destroys the LUKS2 key slots; it does not overwrite sectors. That is the strongest thing a
portable SSD can honestly offer, and it holds only if the volume key was never escrowed off the
device — so a device told its key is escrowed refuses to erase rather than emit a receipt that
overstates what happened.

The order is the requirement:

    authorise -> verify chain -> export chain -> erase key slots -> receipt

Verification comes before destruction so a broken chain is found while the evidence still exists,
and the export comes before erase so the chain survives the device (F16 R3). The audit domain is
never passed to the eraser. The order is signed in its own domain and names one device: an order for
another device is refused, and an unenrolled device cannot erase at all, because a receipt has to be
bound to an identity for T2 to match it. A domain that fails to erase yields `partial`, not success,
and erase is terminal — an erased device refuses a second erase instead of issuing a second receipt.

## Not proven here

No LUKS2 header is touched: `erase_key_slots` is an injected callable and the real `cryptsetup
luksErase` against a real header does not exist yet, so nothing here demonstrates that the slots
are gone. The F16 acceptance criterion is forensic — "when the disk is forensically examined, then
the data partition is unrecoverable" — and that is a bench result no host-side test can produce; the
receipt-hash match against T2's record is equally unproven, since there is no T2 in this path.

The index is SQLite on a host filesystem, not on a LUKS2 volume on the T1 device, so durability under
power loss, full-partition behaviour and the endurance of the portable SSD are untested. Nothing
supervises the enforcer: `RetentionService.sweep` is called by a test, and the systemd unit or
supervised process that would run it on a schedule independently of the application — the other half
of what "independent service" means — is M04 runtime work that does not exist. Blob deletion is an
injected `unlink`; no clip file is actually removed.
