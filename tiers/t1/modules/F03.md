# F03 — Boot chain and A/B update slots (M02, M03)

**Module:** M02 boot & firmware, with the M03 storage layout · **Subsystem:** S01 · **Controls:** C3, C7
**Depends:** none · **Blocks:** F15 (OTA), F13 (audit continuity), commissioning
**Class:** Platform (brief + code review; bench and field test required)

## What is implemented here

Three of F03's five requirements are *behaviour*, and behaviour can be executed and refuted off the
hardware. `src/t1/platform/boot.py` holds them:

| Requirement | Implementation |
|---|---|
| R3 A/B slots, boot counter, rollback after 3 failed health checks | `report_health` counts *consecutive* failures per slot; the third switches `active` to the other slot, clears the stage record and emits `rolled_back` with the failing version |
| R4 privacy set verified before any application container starts | `Stage.VERIFY_PRIVACY_SET` precedes `Stage.START_CONTAINERS`; a failed signature sets `Mode.INGEST_ONLY` and the container stage never completes |
| R5 audit mounted append-only before any service starts | `Stage.MOUNT_AUDIT` precedes `Stage.START_SERVICES`, and `step_boot` raises `BootOrderError` on any attempt to run a stage out of `SEQUENCE` order |

R1 and R2 — the shim → GRUB2 → signed kernel → signed initramfs chain, and L3's Tangri-owned UEFI
keys — are firmware and image work. Nothing here simulates them; `chain_signed` is an input the
bootloader supplies, so the consequence of an unsigned chain is testable while the verification
itself stays where it belongs.

## Ordering is data, not call order

`SEQUENCE` is the boot order as a value, and `step_boot` refuses any stage whose predecessor has not
completed. The alternative — trusting that the calls appear in the right order in some init script —
is exactly the failure R5 exists to prevent: a service that starts before the audit volume is
mounted append-only has already done work that no chain records.

## Ingest-only is a mode, not a refusal

A failed privacy-set signature does not stop the box. Ingest continues, the bridge is disabled and
containers stay down (R4). A store that stops counting is a support call; a store that leaks with a
tampered filter is a breach, and the two must not be traded for each other.

## The layout is checkable

`src/t1/platform/layout.py` states SPEC §3.1's layout as data and refuses violations by name, in the
same shape as pre-flight:

- `volume_off_t1_device` — AD-01. Every volume T1 writes lives on the Tangri device; a layout
  placing one on the customer's disk is refused before an installer acts on it.
- `audit_not_append_only`, `audit_too_small` — the 8 GB append-only audit partition. Audit is its
  own `Volume`, so "survives a rootfs rollback" is structural rather than conventional.
- `data_not_encrypted`, `rootfs_writable` — LUKS2 on data and spool, read-only root slots.
- `swap_on_disk`, `zram_absent` — swap on the boot SSD is prohibited; 512 MB of zram is the only
  swap.

## Source and tests

`src/t1/platform/boot.py`, `src/t1/platform/layout.py`, `tests/test_boot.py` (one test per F03
acceptance criterion, plus the layout invariants and the ordering guard).

## Not proven here

Everything physical: that a real host boots the shim chain from the Tangri SSD without touching the
internal disk, that RAUC writes the inactive slot and switches it, that the audit partition mounts
append-only from initramfs before systemd reaches its first service, and that a rollback preserves a
contiguous, verifying audit chain across the switch. Those are bench gates, and the green suite here
is not evidence for any of them.
