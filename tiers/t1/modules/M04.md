# M04 — Unit supervision and activation refusal

**Module:** M04 container runtime · **Subsystem:** S01 · **Controls:** C3, C8, C14
**Decides against:** [D-010](../../../canon/05-decisions/0010-d010-unit-decomposition-and-release.md) (answers ADR-REQ-007), D-006, D-003, D-009
**Depends:** F03 (`Stage.START_CONTAINERS`) · **Blocks:** M08, M12, M14
**Class:** Platform (brief + code review; bench test required)

## The four units

D-010 fixes the decomposition, and `Unit` is that list in start order:

```python
START_ORDER = (CONTROL_PLANE, EGRESS_FILTER, BRIDGE, SEALED_PIPELINE)
```

The order is a safety property, not a convenience. `BRIDGE` depends on `EGRESS_FILTER` so no path to
T2 can exist before the policy constraining it is live; `SEALED_PIPELINE` is last because it is the
only unit that ever holds unredacted pixels, and it will not start until the control plane can audit
what it does.

## Activation is refusable

`Supervisor.activate` returns a supervisor, never an exception, because a customer site needs the
rest of the device up and a precise statement of what did not start. Each refusal is a `UnitFinding`
with a remedy:

| Finding | Meaning |
|---|---|
| `version_unknown` | the artifact declares no version, so nothing can be reconciled against it |
| `signature_invalid` | signature verification before activation (F03 R4), per unit |
| `scope_exceeded` | the unit asked for a credential outside `PERMITTED_SCOPES[unit]` |
| `dependency_not_running` | the units above it in the order are not up |
| `sealed_environment_unsealed` | the sandbox offered the sealed unit network, writable paths, core dumps or swap |
| `health_lost` | the unit stopped answering; it is `FAILED`, not assumed alive |

The version is inside the signed payload:

```python
payload = f"{ARTIFACT_SIGNING_DOMAIN}:{unit.value}:{version}".encode()
```

so re-labelling a signed artifact with an older version does not produce an older release, it
produces a forgery — which is the same shape as the egress policy's monotonic floor and is deliberate:
D-003 lets the policy bundle ship on its own, and a rollback of it must be as hard as a rollback of
the runtime.

## Least privilege as a closed set

`PERMITTED_SCOPES` is an allow-list per unit, and activation checks subset rather than membership,
so a new scope has to be granted deliberately. A test asserts the sealed unit's scopes are disjoint
from the bridge's: the unit holding pixels and the unit holding the network share nothing.

## Source and tests

`src/t1/platform/supervisor.py`, `tests/test_supervisor.py`. `SealedEnvironment` is reused from
`src/t1/sealed/guard.py` rather than restated, so the supervisor and the sealed process cannot
disagree about what sealed means.

## Not proven here

This is the supervision *policy* with no runtime behind it yet. Nothing here creates a namespace,
drops a capability, applies a seccomp profile or launches a process; the real supervisor (systemd
units or a container runtime — the runtime choice is still open) must enforce the same refusals, and
`sealed-probe` must run against it rather than against the type system. A green suite here says the
rules are consistent, not that anything is confined.
